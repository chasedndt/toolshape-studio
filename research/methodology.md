# Research methodology

## Questions

Research is organised around decisions:

- What makes an application harness-native rather than merely API-accessible?
- Which control paths reduce GUI grounding failure?
- Which state/evaluation methods detect collateral damage?
- How should authority, secrets, and untrusted data be separated?
- Which product outcomes belong in the first 80/20 feature set?
- How can professional and personal style be represented and evaluated?
- Which local/hosted/open-source boundaries support trust and a viable business?

## Source priority

1. current official specifications and platform documentation;
2. current official product documentation for outcome baselines;
3. government/standards/security guidance;
4. primary research papers;
5. official open-source project documentation;
6. respected books/practitioner writing;
7. secondary summaries only for discovery, not load-bearing claims.

## Temporal discipline

- record access/publication date;
- distinguish product release date from page update date;
- treat post-2025 protocols/products as unstable until rechecked;
- never assume a current model, licence, CEO, pricing, provider policy, or product feature from memory;
- refresh before build milestones.

## Clean-room discipline

Use product research to identify user outcomes, pain points, capability categories, and quality expectations. Create original domain models, interaction patterns, copy, assets, and implementation.

## Research note template

```text
Source and date
Source type and trust
What it directly says
What it does not establish
Design implication
Competing interpretation
Experiment/eval required
Decision status
```

## Preprint discipline

A preprint can suggest useful architecture or benchmarks. It does not become settled fact merely because it has precise numbers. Record:

- peer-review status;
- dataset/task limitations;
- replication status;
- possible benchmark leakage or evaluator weakness;
- whether the result applies to Toolshape’s domain.

## Product-feature discipline

Competitor marketing may omit limitations. Requirements based on it must be validated by independent testing and user evidence.

## Book/archive discipline

Store summaries and source links, not copyrighted full text. Future chapters should cite the original sources and clearly label Toolshape-specific proposals such as ANAC.
